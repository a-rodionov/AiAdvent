Пограничные случаи

1. config_loader.py — содержит ServerConfig (серверное) и resolve_completion_config /
   serialize_completion_config (относится к domain model CompletionConfig). Нужно разделить.
2. json_helpers.py — create_model_from_schema используется в config_loader для output_config. Чисто
   утилитарный код, но привязан к конфигурации CompletionConfig.
3. client.py — TUI-клиент импортирует ws_protocol.py из adapter/inbound/web/. Это протокол
   WebSocket-фреймов, который является частью серверного контракта, но используется и клиентом.
4. adapter/outbound/llm/llm_adapter.py — реализация LLM-порта через any-llm. Это адаптер, но к какому
   проекту он ближе? Сейчас это единственная реализация ILlmPort.

Ключевые решения и открытые вопросы

1. Куда отнести llm_adapter.py (адаптер any-llm)?

Вариант A — Оставить в серверном проекте (текущее предложение).

- (+) core остаётся чистым, без зависимости от any-llm SDK
- (+) Другие потребители core могут использовать свои LLM-адаптеры
- (−) Каждый потребитель вынужден реализовывать адаптер с нуля

Вариант B — Вынести в отдельный пакет llm-agent-adapters или включить в core как optional extra
(llm-agent-core[any-llm]).

- (+) Готовый адаптер из коробки
- (+) core всё ещё не зависит обязательно от any-llm
- (−) Ещё один пакет для управления

Вариант C — Включить в core, сделать any-llm обязательной зависимостью.

- (+) Прост в использовании
- (−) Нарушает гексагональный принцип: core зависит от конкретного SDK

Моя рекомендация: Вариант A для начала. Адаптер — это инфраструктурный код. Если появится второй
потребитель, тогда можно выделить adapters-пакет.

2. Куда отнести config_loader.py?

Сейчас он содержит смешанную логику:

- ServerConfig — чисто серверное (host, port, log_level, session_storage_path)
- resolve_completion_config / serialize_completion_config — работа с CompletionConfig, который является
  доменной моделью core

Предложение: разделить файл:

- ServerConfig + get_server_config() → остаётся в server (infrastructure/config_loader.py)
- resolve_completion_config / serialize_completion_config → тоже в server, так как это file I/O логика
  для загрузки конфигов, а core не должен знать о файловой системе

3. Что с json_helpers.py?

create_model_from_schema используется только в config_loader.py для построения динамической Pydantic
модели из JSON Schema файла. Это инфраструктурная утилита → остаётся в server.

4. Что с client.py?

Клиент импортирует app.adapter.inbound.web.ws_protocol — модуль WebSocket-фреймов. Это контракт обмена
сообщениями между клиентом и сервером.

Варианты:

- Выделить ws_protocol.py в shared-пакет (если клиент и сервер — разные проекты)
- Оставить в server и клиент зависит от server (нежелательно)
- Дублировать (нежелательно)

Рекомендация: ws_protocol — это ни бизнес-логика агента, ни серверная логика. Это контракт API. На
данном этапе проще оставить его в серверном проекте, а клиент сделать частью того же проекта. Если
клиент когда-то станет отдельным приложением, тогда выделить контракт.

5. Нарушение гексагональности: context_strategy.py зависит от ILlmPort

Это уже отмечено в ваших openspec changes. MessageContextStrategy (domain/model) зависит от ILlmPort
(port/outbound) — внутренний слой зависит от внешнего:

domain/model/context_strategy.py → port/outbound/llm_port.py
▲ внутренний слой ▲ внешний слой

При выделении core это нужно исправить — иначе циклическая связь domain ↔ port сохранится и в пакете.

Порядок реализации

1. Подготовка core
   ├── Исправить циклическую зависимость context_strategy → llm_port
   ├── Создать pyproject.toml для llm_agent_core
   ├── Перенести domain/ и port/ в новый пакет
   └── Адаптировать внутренние импорты

2. Адаптация серверного проекта
   ├── Заменить app.application._ → llm_agent_core._
   ├── Переместить common/ → infrastructure/
   ├── Обновить composition root
   └── Обновить pyproject.toml — добавить зависимость от core

3. Тесты
   ├── Доменные тесты → core
   ├── Use case тесты → core (или server, если нужны моки адаптеров)
   └── Интеграционные → server

4. CI/CD
   └── Настроить сборку и публикацию core отдельно

Вопросы к тебе

1. Монорепо или два репозитория? Монорепо с workspace (например, через hatch или uv workspace) проще для
   разработки. Два репозитория — чище для независимого релиза. Что предпочтительнее?
2. Адаптер any-llm — согласен с Вариантом A (оставить в server), или предпочитаешь optional extra в
   core?
3. Клиент — оставляем в серверном проекте или рассматриваем третий пакет?
4. Именование пакета — llm_agent_core подходит, или есть предпочтения по названию?
