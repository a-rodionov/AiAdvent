● Hexagonal Architecture: Application vs Presentation Layers

  In hexagonal (Ports & Adapters) architecture, the hexagon has a strict
  inside/outside split:

          ┌─────────────────────────────────┐
          │         OUTSIDE THE HEX         │
          │  (Adapters — all I/O concerns)  │
          │                                 │
          │  ┌───────────────────────────┐  │
          │  │       INSIDE THE HEX      │  │
          │  │  (Domain + Application)   │  │
          │  │                           │  │
          │  │  ┌─────────────────────┐  │  │
          │  │  │      DOMAIN         │  │  │
          │  │  │  (pure business     │  │  │
          │  │  │   logic / entities) │  │  │
          │  │  └─────────────────────┘  │  │
          │  │                           │  │
          │  │  APPLICATION LAYER        │  │
          │  │  (use-cases / services)   │  │
          │  │  defines Ports (ABCs)     │  │
          │  └───────────────────────────┘  │
          │                                 │
          │  ADAPTERS (infrastructure):     │
          │  - Driving: HTTP, WebSocket,    │
          │    CLI, test harness            │
          │  - Driven: DB, LLM API, files   │
          └─────────────────────────────────┘

  Application Layer (inside the hex)

  Purpose: Orchestrates use-cases. Coordinates domain objects to fulfill a
  request — but contains no business rules itself and no I/O.

  Key role: Defines the Ports — abstract interfaces (ILlmPort,
  ISessionRepository) that describe what the application needs from the outside
  world, without knowing how it's implemented.

  What belongs here:
  - Use-case classes / service classes (SessionService)
  - Port definitions (ABCs for LLM, persistence, etc.)
  - Application-level events and DTOs that cross the port boundary

  What does NOT belong here: FastAPI, HTTP schemas, file system, database
  drivers, third-party SDK calls.

  ---
  Presentation Layer (outside the hex — a "driving adapter")

  Purpose: A driving adapter — it drives the application by translating an
  external trigger (HTTP request, WebSocket frame, CLI command) into a call on
  the application layer.

  In hexagonal terms, there is no distinct "presentation layer" — it is simply
  an adapter that happens to handle HTTP/WS. Its job is to translate, not to
  orchestrate:

  HTTP Request → [Presentation Adapter] → Application Port → [Application
  Service] → Domain

  What belongs here:
  - FastAPI route handlers
  - WebSocket frame parsing/sending
  - HTTP request/response Pydantic schemas
  - create_app() wiring

  What does NOT belong here: Business logic, persistence, or domain state
  mutations.

  ---
  Why this matters for the proposed design

  The current proposal calls the folder presentation/ — this is a naming 
  convention from layered architecture (MVC-style), not hexagonal. In strict
  hexagonal terminology it would be called adapters/driving/http/ or similar.

  The practical implication: the presentation/ folder in the proposal is correct
   in intent (no business logic, only translation), but if you want to be strict
   about hexagonal naming, consider:

  app/
    domain/
    application/      ← inside the hex
    adapters/
      http/           ← driving adapter (was "presentation")
      llm/            ← driven adapter (was infrastructure/llm_adapter.py)
      persistence/    ← driven adapter (was
  infrastructure/session_file_adapter.py)
      config/         ← driven adapter (was infrastructure/config_loader.py)

  Would you like the architecture adjusted to use this stricter hexagonal 
  structure, or keep the layered infrastructure/ + presentation/ naming that was
   proposed?

❯ context_strategy.py contains algorithms for processing part of session state. 
 Why they are not in domain layer?                                              

● You're right to question this. Let me reason through it carefully.

  Why they should be in the domain layer

  The context strategies are algorithms that operate on domain entities —
  specifically MessageRecord lists owned by Session. They answer a domain
  question: "given this session's history, what messages should be sent to the 
  LLM?"

  - DummyStrategy — return all records as-is. Pure function on domain data.
  - SlidingWindowStrategy — keep last N records. Pure function on domain data.
  - SummaryStrategy — compress history when over threshold. Uses ILlmPort — but
  ILlmPort is already in domain/interfaces/, so this import doesn't violate the
  dependency rule.

  The dependency direction is still correct:

  domain/services/context_strategy.py
      imports → domain/entities/session.py     ✓ (domain → domain)
      imports → domain/interfaces/llm_port.py  ✓ (domain → domain/interfaces)

  No upward dependency. Nothing from use_cases/ or adapters/ is imported.

  The reason I put them in use_cases/ was conflating "calls the LLM" with
  "orchestration". But SummaryStrategy doesn't orchestrate a business workflow —
   it calls the LLM as part of a domain algorithm. The distinction is intent:
  this is compression logic applied to session state, not coordination between
  separate domain objects.

  The correct home in Clean Architecture is a domain service — a stateless class
   that implements domain logic that doesn't naturally belong on a single
  entity:

  app/domain/
    entities/
      session.py
    value_objects/
      completion.py
      pricing.py
    services/                          ← new
      context_strategy.py              ← moves here
    interfaces/
      llm_port.py
      session_repository.py

❯ What is domain services?                                                      

● Domain Services

  A domain service is a stateless class that implements domain logic which
  doesn't naturally belong on a single entity or value object.

  The test is simple: if a piece of logic involves domain rules but doesn't have
   a natural home on one specific entity, it's a domain service.

  ---
  The three DDD building blocks and when each applies

  ┌────────────┬──────────────────────────┬────────────────────────────────┐
  │ Building   │       Owns state?        │    Example in this codebase    │
  │   block    │                          │                                │
  ├────────────┼──────────────────────────┼────────────────────────────────┤
  │ Entity     │ Yes — has identity,      │ Session — has an ID,           │
  │            │ changes over time        │ accumulates messages           │
  ├────────────┼──────────────────────────┼────────────────────────────────┤
  │ Value      │ No — immutable,          │ CompletionConfig, TokensUsage  │
  │ object     │ identified by value      │                                │
  ├────────────┼──────────────────────────┼────────────────────────────────┤
  │ Domain     │ No — stateless algorithm │ MessageContextStrategy         │
  │ service    │  over domain objects     │                                │
  └────────────┴──────────────────────────┴────────────────────────────────┘

  ---
  Why MessageContextStrategy is a domain service

  It implements a domain algorithm — "given a session's message history, which 
  messages are relevant to send?" — but:

  - It doesn't belong on Session because the strategy is a pluggable policy, not
   intrinsic to what a session is. Session shouldn't know about sliding windows
  or summarization.
  - It doesn't belong on MessageRecord (a value object) because it operates
  across the whole list, not on one record.
  - It's stateless — it transforms domain data but holds none of its own.

  That's the domain service niche: algorithms that span entities/value objects,
  are part of the domain's rules, but have no natural owner.

  ---
  What makes it still domain (not use-case or infrastructure)

  SummaryStrategy calls ILlmPort — but ILlmPort is defined in
  domain/interfaces/. The import is:

  domain/services/context_strategy.py
      → domain/interfaces/llm_port.py   ✓ (domain → domain)
      → domain/entities/session.py      ✓ (domain → domain)

  No upward dependency. The LLM here is used as a compression tool for domain 
  data, not to coordinate a business workflow between different aggregates. That
   keeps it in the domain ring.

  Compare to SendMessageUseCase — that coordinates: load session, apply
  strategy, call LLM, persist result, return events. That coordination across
  multiple domain objects is what puts it in use_cases/.

  ---
  The practical rule of thumb

  ▎ If removing the class would break the domain model's internal consistency 
  rules → domain service.
  ▎ If removing the class would break a workflow that involves multiple domain 
  objects or I/O → use case.

  - The classification test for aggregate component vs. domain service is
  simple: can two different sessions share one strategy instance? No — each
  session needs its own _summary and _record_list. That shared-state
  impossibility is the signature of an aggregate component.

  aggregate. Use cases and adapters hold a Session reference, but they never
  directly access or mutate the strategy. Session delegates to it internally.
  This is why context_strategy.py can live next to session.py without exposing
  the strategy in ISessionRepository's interface.

  strategy state (_summary, _window_size, strategy type) so SessionFileAdapter
